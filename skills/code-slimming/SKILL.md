# 代码瘦身之道

## 核心信条

AI的代码膨胀不是能力问题，是价值倾向问题。AI默认认为"多比少安全"，而真相是**少比多安全**。

同样的预算，宁愿写少不够再补，也不要写多了删不动。代码的安全状态是：**每一行都删不掉**。如果一段代码可以通过删减而不改变行为，那这段代码现在就是错的——不是未来可能错，是现在就已经错了。

## 三种膨胀形态

| 类型   | 表现                           | 处理策略              |
| ---- | ---------------------------- | ----------------- |
| 表层膨胀 | 废话注释、未使用导入、重复逻辑块             | Linter处理，不值得此技能出手 |
| 深层膨胀 | 为"未来可能需要"提前设计的抽象层、接口、配置项     | 反模式清单 + 膨胀信号检测    |
| 结构侵蚀 | 代码长错位置——业务逻辑泄漏到路由层，展示逻辑入侵业务层 | 最致命，必须重写          |

**此技能只对付深层膨胀和结构侵蚀。**

## AI 膨胀反模式 Top 10

**写任何代码之前，先过一遍这个清单。这比任何架构模板都管用。**

| #   | 反模式             | 表现                                  | 正确做法                       |
| --- | --------------- | ----------------------------------- | -------------------------- |
| 1   | **抢跑抽象**        | 还没第二个使用者就建抽象层、接口、策略模式               | 等出现第3个实例再抽象（Rule of Three） |
| 2   | **防御性编码表演**     | 到处检查null、捕获所有异常，但不做有意义的处理           | 只在能合理恢复的地方捕获，否则让异常传播       |
| 3   | **接口恋物**        | 每个类都配一个接口，"以备将来替换实现"                | 直到真正需要替换实现时才提取接口           |
| 4   | **配置成瘾**        | 硬编码能搞定的事非要做成可配置、可插拔                 | 先硬编码，等到有人真的需要改它时再配置化       |
| 5   | **过早DRY**       | 看到两处相似代码就抽函数                        | 重复<3次是安全的，复制粘贴比错误抽象更好      |
| 6   | **层级增殖**        | 多加一层"以防万一"——多一个Service、多一个Wrapper   | 每一层必须有不可替代的职责，否则删除         |
| 7   | **注释叙述**        | 用注释复述代码在干什么（`// 遍历列表` `i++ // i加1`） | 只写"为什么"的注释，代码本身说明"是什么"     |
| 8   | **参数爆炸**        | 5个参数的函数，其中3个有默认值或经常传null            | 超过3个参数就考虑用对象/结构体封装         |
| 9   | **文件蔓延**        | 一个文件能放下的东西拆成三个——"为了关注点分离"           | 增量追加到已有文件，除非文件已超过合理规模      |
| 10  | **未来-proofing** | 为"将来可能"的需求写代码——预留扩展点、配置项、回调         | 只为当前的需求写代码，YAGNI           |

## 价值序列（优先级从高到低）

```
代码在正确的位置 > 代码行数少
代码行数少 > 抽象层级多
重复<3次是安全的 > 消除重复
先硬编码 > 先配置化
让异常传播到能处理的层级 > 无条件吞掉异常
增量追加已有文件 > 创建新文件
代码自解释 > 写注释解释
追问确认需求 > 基于假设直接编码
50行能跑的代码 > 200行"更优雅"的代码
不改变行为的前提下删减 > 保留膨胀代码
改变行为的删减 = 错误，必须回退
测试友好度 > 行数最少
```

## 执行流程

根据场景和规模选择对应流程：

### 判断规模

- **快速模式**：改动 < 50行，不新建文件
- **完整模式**：改动 ≥ 50行，或需要新建文件

---

### 场景A：新功能开发

#### A-1. 快速模式（改动 < 50行，无新文件）

直接实现。完成后执行膨胀自检（见下方清单）。

#### A-2. 完整模式（改动 ≥ 50行，或需要新建文件）

**第1步：意图确认（必做）**

写任何代码之前，先输出：

- 这个功能的核心目标是什么？（一句话）
- 需要修改哪些已有文件？列出文件路径
- 需要新建几个文件？如果 > 0，说明每个新文件的必要性
- 最简实现是什么样的？（先描述最笨的版本）

**输出后等待用户确认。**

需求模糊时的两条路径：

- **路径A（默认）**：追问确认 → 按约束生成
- **路径B（用户明确选择"先实现"）**：允许生成，但必须在相关代码顶部标记 `// [HYPOTHESIS] 此处基于假设：xxx。若假设不成立，需回退重写。`

**第2步：最小实现**

从最笨的版本开始写，然后只在必要时增强：

1. 先写一个能跑的版本——用最直接的方式，不考虑"优雅"
2. 检查是否有膨胀信号（见自检清单）
3. 只在信号出现时才增强——不是为了"未来可能"，而是为了"现在就需要"

**禁止的行为**：

- 在只有一个使用者时就提取接口/抽象
- 为"将来可能需要"预留扩展点
- 把简单逻辑拆成多个"步骤方法"来"提高可读性"
- 创建新文件来"分离关注点"（除非已有文件确实过大且职责明确不同）

**第3步：膨胀自检（必做）**

生成代码后，对照膨胀信号清单逐项检查（见下方）。

**任何一项信号触发，立即修改对应代码，不得输出给用户。**

---

### 场景B：代码重构 / 架构优化

#### 第1步：现状诊断

逐文件扫描，输出问题清单：

- 哪些代码属于深层膨胀？（为"未来"设计的抽象、接口、配置）
- 哪些代码属于结构侵蚀？（代码出现在错误位置）
- 哪些文件可以合并？哪些类/函数可以删除？
- 哪些抽象层实际上只有一个实现？

#### 第2步：瘦身方案

对每个问题给出具体删减动作：

- 删除哪些类/接口/方法
- 合并哪些文件
- 将哪些代码迁移到正确位置
- 哪些"抽象"可以还原为具体实现

**方案必须满足：删减后行为不变。**

#### 第3步：执行 + 验证

执行删减后逐项确认：

- 行为是否改变？（改变则回退）
- 文件数是否减少？
- 抽象层级是否减少？
- 职责边界是否更清晰？

---

### 场景C：代码审查

#### 第1步：对照反模式清单扫描

逐文件扫描，标记以下问题：

- 触发哪些膨胀反模式（引用Top 10中的编号）
- 哪些代码属于结构侵蚀
- 膨胀信号是否触发（见自检清单）

#### 第2步：输出审查报告

对每个问题输出：

- 位置：文件路径 + 行号范围
- 类型：引用反模式编号 + 具体描述
- 建议：**具体的删减动作**（不是泛泛的"可以考虑简化"）

**只输出可执行的具体建议，不输出泛泛的"代码风格"评价。**

---

### 场景D：修复结构侵蚀

#### 第1步：识别侵蚀点

标记所有职责跨界的代码——代码出现在了不属于它的层级/文件中。

通用判断标准（不绑定特定框架）：

- **路由/入口层**：只负责接收请求、调用业务逻辑、返回响应
- **业务逻辑层**：只做业务编排和数据转换
- **数据层**：只做持久化操作
- **数据载体**：只有字段，没有逻辑

#### 第2步：迁移代码

将跨界代码迁移到正确位置。

#### 第3步：验证边界

确认迁移后每层职责单一。

## 膨胀信号自检清单

**不绑定具体行数，而是检测结构性信号。** 这些信号比行数更能反映真正的膨胀。

| 信号            | 阈值         | 处理方式                           |
| ------------- | ---------- | ------------------------------ |
| 函数做几件事        | > 2件       | 拆分为多个函数                        |
| 嵌套深度          | > 3层       | 提前return / guard clause / 提取函数 |
| 函数参数个数        | > 4个       | 用对象/结构体封装相关参数                  |
| 文件/模块职责数      | > 1个       | 考虑拆分文件                         |
| 抽象层级数         | > 必要层级 + 1 | 删除多余层                          |
| 重复出现次数        | < 3次       | 不抽象，保持重复                       |
| 只有一个实现的接口/抽象类 | ≥ 1个       | 删除接口，保留具体实现                    |
| 注释类型          | "是什么"注释    | 删除注释，让代码自解释                    |
| 未使用的导入/变量     | ≥ 1个       | 删除                             |
| 异常捕获但不处理      | ≥ 1个       | 要么处理，要么让它传播                    |

### 关于行数的参考指引

行数不是硬约束，但以下参考值有助于建立直觉：

| 代码类型             | 参考上限  | 说明               |
| ---------------- | ----- | ---------------- |
| 路由/入口函数          | ~15行  | 接收→调用→返回，不做其他事   |
| 业务函数             | ~40行  | 超过说明函数做了太多事      |
| 数据载体(DTO/struct) | ~10行  | 只有字段定义，没有逻辑      |
| 单个文件总行数          | ~300行 | 超过考虑拆分（但不要为了拆而拆） |

**参考值 ≠ 硬约束。** 超过参考值时检查膨胀信号，信号没触发就不需要动。

## 语言/框架适配指南

核心原则不变，但具体实践随语言调整：

### Java / Spring

- Controller 只做路由转发，不含业务逻辑
- Service 做业务编排，不超过必要复杂度
- DTO/Record 只做数据载体，不含逻辑
- 不要为每个 Service 都建 Interface（除非有多个实现或需要Mock测试）
- 异常：在最近能合理处理的层级捕获；Service 层的跨服务调用允许必要的异常处理（降级、重试）

### Go

- 少用接口——Go 的接口是行为的事后抽象，不是事前设计
- 错误必须处理，但不要过度包装——`fmt.Errorf("xxx: %w", err)` 够了
- 不要过早建 package——一个 package 能放下就别拆

### Python

- 不要过度 OOP——函数能解决的不要建类
- 善用标准库——很多"需要框架"的场景标准库已经解决了
- Type hint 是好的，但不要为此建一堆 TypedDict/Pydantic model

### 前端 (React/Vue)

- 组件不要过度拆分——一个组件200行比10个20行的组件更好理解
- Hook/Composable 不要提前抽——等第二个组件需要相同逻辑时再抽
- 不要为"可能需要的状态管理"提前引入 Redux/Pinia

### 通用

- **Rule of Three**：重复出现1-2次，保持原样；第3次再抽象
- **YAGNI**：你不会需要它。不为"未来可能"写代码
- **KISS**：保持简单。最直接的实现往往是最好的

## 测试规则

### 测试代码不受膨胀信号约束

生产代码的自检清单不适用于测试代码。测试的可读性和明确性优先于精简。

### 可测试性优先于行数

如果一个函数因为太大而难以测试，允许拆分——但拆分必须有语义意义（按业务步骤拆），不是为了凑数。

### 禁止为满足精简约束而牺牲可测试性

精简是手段，可维护性才是目的。

## 模板约束规则

### 最小实现先行

每个功能先写最笨的、最直接的版本。只在膨胀信号触发时才增强。AI没有"先设计再填空"的自由度，就没有膨胀的空间。

### 位置硬约束

每种代码只能出现在正确的位置。路由层只做转发，业务层只做编排，数据载体只做搬运。职责跨界 = 结构侵蚀 = 必须重写。

### 追问机制

当用户的需求模糊到AI可以"自由发挥"时，默认先追问确认。但提供快速通道：

- 若用户明确选择"先实现"，允许跳过追问，但必须标记 `[HYPOTHESIS]`
- 模糊的需求是膨胀的温床，标记的假设需在后续迭代中验证或回退

### 增量优先

新功能必须追加到已有文件中，除非有明确的理由创建新文件。新增文件数 = 0 是默认值，每增加一个文件都需要理由。

### 重复容忍

重复代码在出现 < 3 次时是安全的——甚至是优选的。不要因为看到两处相似代码就急于抽象。错误的抽象比重复更难修复。
